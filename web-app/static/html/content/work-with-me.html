About

Why I build this way

I spent about ten years inside enterprise teams — fintech, ed-tech, car diagnostics, developer tools. After a while you notice what actually matters: what breaks in production, what meetings never fix, and what makes users stop trusting you.

That's why I build my own tools — but on native web tech, by extending it, not by reinventing solutions the browser and Node already give you. HTML, CSS, JavaScript, ordinary servers. If something already works, I use it. If it's missing a piece I need every day, I extend it. I don't replace the platform with a second platform that needs its own build step, lifecycle, and rewrite every two years.

That does not mean I only build simple products. Extending native tech is how I ship complex ones without drowning in architecture theatre.

I work as a solo developer by default, one client at a time, from Tbilisi. You talk to the person writing the code. If the project needs a designer or a business partner, I can work with them — I've done that before. Hosting stays on a normal VPS. I use AI when it saves time — it doesn't decide anything for me.

How I work

Habits I picked up the hard way
Simple tools, hard problems

Complexity belongs in the product — auth, billing, permissions, notifications — not in the framework tree. If the browser or Node already does the job, I use that.

I do the whole thing

Design, code, deploy — me. No hand-off between “frontend guy”, “backend guy”, and “DevOps guy”. Usually something real is running in about two weeks.

One client

When I'm on your project, I'm not half-listening in three other Slack workspaces. We talk, we agree scope, I write code.

If it works, leave it

Working and fast enough? We don't rewrite it because a new framework dropped. Upgrades when there's a reason.

One system

One app beats twenty microservices. A VPS beats managed cloud when a VPS is enough. Thirty lines of code beats another monthly SaaS bill.

Test what people do

Login, pay, book a lesson — real flows in the browser. Mocked unit tests that pass while the site is broken don't impress me.

No fashion projects

We don't add layers because everyone else is adding layers. Fashion moves on. Your codebase has to stay usable.

Deploys in seconds

A fix should be live quickly. If shipping takes forever, the product stops improving — and that's your business losing, not just “tech debt”.

Readable code

Open a file and understand it. No magic. No clever one-liner that needs a sermon in the comments.

My stack

Small on purpose — built for real products, not demos

People hear “HTML and vanilla JS” and assume brochure websites. Look at the projects above before you decide that. The stack is simple so the product can be complicated — payments, scheduling, realtime video, domain-specific engines — without turning every feature into a framework migration.

EHTML — HTML that does more

I didn't invent a new file format. I extended HTML. Lists, heavy forms, partial page updates, shared markup — a lot of what people reach for a SPA for can stay in the page. No build step. No bundler. No transpile circus.

e-ui — UI on top of the browser

Buttons, forms, panels, dialogs — same behaviour across the product, built on what the browser already gives you. I use it so pages look designed without rewriting CSS from scratch for every screen.

nodes.js — the server side

Same idea on the server: Node.js without ten frameworks on top. Logins, billing, scheduling, APIs. Cluster support so the app uses the whole machine, comes back if a worker dies, and can restart for a deploy without taking everything offline. Ordinary VPS. When something breaks at 2 a.m., you're not hunting through six layers of abstraction.

Boring infrastructure still matters: careful migrations, the same deploy every time, Stripe for money, Postmark for email. I don't wire in fifteen SaaS tools when thirty lines of code does the job.

FAQ

Straight answers
If your tools are simple, can you still build a complex product?

Yes. Simple tools are not the same as a simple product. InstruxMusic has scheduling, Stripe billing, WebRTC classrooms, messaging, white-label branding, org management. Unison has a language and an engraving engine. I keep the stack small so that complexity stays where it belongs — in the domain — not in the build pipeline.

How much does a project cost compared with an agency?

Agencies often quote $50k–$150k+ and then spend months in meetings. I build the whole thing — design, code, servers, launch — from $10k a month. Discovery is free.

Why one developer instead of an agency?

I'm solo as a developer by default — design systems, frontend, backend, servers, deploy. You talk to the person writing the code, not through an account manager. That doesn't mean I refuse to collaborate. I've worked with strong designers and business people before, and I can plug into that kind of team easily when the project needs it. What I avoid is agency overhead: five roles, weekly syncs, and nobody who owns the whole product.

What's different about how you build?

Plain HTML, a little JavaScript, and libraries I wrote — EHTML, e-ui, nodes.js. No microservice maze. No managed cloud when a VPS is enough. Deploys in seconds. Software that should still make sense in a few years.

How long does an MVP take?

Something usable in about two weeks, usually. A full MVP often under three months, including product decisions — not just tickets. I've shipped that solo while bigger teams were still planning.

Do you work remotely?

Yes. Worldwide, from Tbilisi. One client at a time. US and European hours are fine.

What do you usually build?

Business apps, SaaS, booking, payments, internal tools, startup MVPs. Recent solo work: InstruxMusic and Unison. Before that: fintech, ed-tech, automotive diagnostics.

Can you improve an existing codebase instead of rebuilding?

Yes. Legacy rescue is $3k a week. Fix what's broken, remove what's unused, ship something useful every week. Full rewrite only when there's no better option.
